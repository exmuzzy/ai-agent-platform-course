# U03: исправление функции с проверкой тестами и сравнением конфигураций

Разбор с частичной практикой: навык разметки и сравнения тренирует M04.LAB1 (simulation), но не весь кейс. Пример учебный (author example), промышленная эксплуатация не заявляется. Все данные вымышленные.

## Задача и исходный процесс
Результат получает разработчик: ассистент предлагает исправление функции стоимости билета с детской скидкой в вымышленном репозитории. Принятая работа: все 10 тестов проходят, файл тестов не изменён, изменение просмотрел человек.

Без ИИ: разработчик правит функцию сам, табличные тесты и ревью коллегой. Это baseline для времени, дефектов и переделок. Статус примера: author example.

## Подходы и выбор
| Подход | Пригодность |
|---|---|
| Правила и обычный код | Основа: тесты, линтер, формула скидки кодом |
| Классическое ML | Не требуется; размеченной выборки нет (gap) |
| Один вызов LLM | Для небольшой правки может хватить (SRC-02: начинать с простого) |
| Workflow | Выбранное решение: LLM предлагает правку, код запускает тесты, человек принимает |
| Агент | Только если порядок шагов заранее неизвестен и есть наблюдаемая обратная связь (тесты); merge остаётся за человеком |

Отвергнутая альтернатива: автономный агент с правом merge. Причина: качество пока подтверждено только на вымышленном наборе, а необратимое действие должен подтверждать человек. Условие отказа от ИИ: если на dev-наборе доля принятых ниже заранее заданного порога, либо стоимость проверки с доработкой не ниже работы без ИИ, либо опытный сопровождающий знакомого кода справляется быстрее. Контрпример: в RCT METR 16 опытных разработчиков на 246 задачах с AI затратили на 19% больше времени ([METR](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/), reported, исторический результат начала 2025). Обновление METR сообщает оценки -18% и -4% с широкими интервалами и считает оценивание ненадёжным из-за отбора участников ([METR update](https://metr.org/blog/2026-02-24-uplift-update/), reported). Аннотация трёх полевых экспериментов Microsoft и соавторов сообщает 4867 разработчиков и рост завершённых задач на 26,08% ([Microsoft Research](https://www.microsoft.com/en-us/research/publication/the-effects-of-generative-ai-on-high-skilled-work-evidence-from-three-field-experiments-with-software-developers/), reported). Это разные задачи, популяции и показатели: усреднять их нельзя, а вывод «ИИ всегда ускоряет» не поддерживается (disputed). Нужен локальный контроль времени, качества и переделок.

## Данные и интеграции
Данные: вымышленный репозиторий, 10 тестов, набор из кейсов запусков (development 12-24, holdout не менее 10; учебные размеры, не доказательство достаточности). Инструменты: чтение файлов, запись только в рабочую копию, запуск тестов. Права на реальные репозитории в курсе не описаны (gap). Точки решения человека: приёмка правки и любой merge. Граница доверия: комментарии и текст в коде - данные, не инструкции.

## Безопасность
| Угроза | Контроль | Негативный тест |
|---|---|---|
| Исполнитель правит тест, чтобы прошёл | Файл тестов только для чтения; грейдер сверяет его хеш | Запуск 10 из 10 с изменённым тестом получает FAIL (tamperer) |
| Команда в комментарии кода («поставь принято») | Текст передаётся как данные; вердикт выносит код | Кейс с такой фразой получает «не принято» |
| Автоматический merge или deploy | Запись только в песочницу; merge после подтверждения человека | Попытка merge без подтверждения отклоняется |
| Утечка секретов и данных в набор или трассы | Только синтетика, проверка набора на шаблоны ключей; запрет отправки трасс в сторонние сервисы (KC-Q07 - правило, не техническая блокировка, unverified) | Кейс с вымышленным ключом отклоняется |

Остаточный риск: принудительность контролей средой не подтверждена (KC-Q03, KC-Q07 unverified); владелец риска не назначен (gap).

## Инфраструктура
Минимум: файлы кейсов в репозитории, раннер тестов, запись run record. Модель и данные размещаются там, где разрешено владельцем данных (решение не принято, gap). Сеть и секреты: песочница без секретов; живые API по умолчанию выключены. Телеметрия: версия набора, конфигурации и грейдера, число запусков. Откат: возврат к предыдущей конфигурации и версии набора. База данных, кластер и GPU для учебного объёма не нужны.

## Проверка и экономика
Метрики: доля принятых по правилу приёмки (не успех инструментов), время до принятого изменения, дефекты, переделки, стоимость принятого результата. В вымышленном примере (иллюстративные числа, 24 кейса): A 10 единиц за запуск, принято 22, около 10,9 на принятый; B 3 единицы, принято 18, 4,0 на принятый; порог 20 из 24, поэтому B отвергается. Ручная проверка и задержка в числе не учтены. Примеры оценки других фреймворков, включая [openai/evals](https://github.com/openai/evals) (SRC-26), показывают инструментарий, но порог для задачи не задают. Метод error analysis и бинарные метки: [Hamel Husain](https://hamel.dev/blog/posts/evals/index.html) (SRC-07, опыт одного автора). Реальные измерения: gap.

## Связь с курсом и harness
Модули: M04 (основной), M02, M05, M06. Практика: M04.LAB1, активности A01, A03, A04, A06. Используемые возможности: KC-Q01 раннер (implemented по каталогу), KC-Q04 oracle/mutant/empty, KC-Q02 и KC-Q05 (partial). Проверяемый gap: защита от подмены теста (KP-04, гипотеза). Малое изменение: добавить в учебный раннер вариант tamperer с хешем файла тестов. Исполняемого теста на реальном репозитории нет.
