# U06: аналитика, SQL и отчётность

Статус: draft, разбор без исполняемой лабораторной вне симуляции (lab «Read-only помощник» не создан, research/coverage). Оператор, таблицы SYN-TRIPS и SYN-REFUNDS, вопросы и все числа вымышлены (author example). Прочитанного примера текст-в-SQL в базе курса нет, поэтому реального внедрения кейс не описывает.

## Задача и исходный процесс
Получатель результата: руководитель линии и аналитик вымышленного транспортного оператора. Вопросы вида «сколько возвратов по тарифу T за прошлую неделю» и «как менялась доля опозданий по направлениям». Принятая работа: число или таблица, которые аналитик проверил по определению метрики и источнику, с указанием запроса, периода и версии данных. Ответ без указанного запроса и периода не принимается.

Как решается без ИИ (baseline): готовый отчёт в BI с семантическим слоем (определения метрик в одном месте), либо аналитик пишет SQL вручную. Для повторяющихся вопросов отчёт или параметризованный запрос обычным кодом дешевле и надёжнее. Источник примера: author example.

## Подходы и выбор
| Подход | Повторяющиеся вопросы | Новые вопросы по известной схеме | Нестандартная аналитика, прогноз |
|---|---|---|---|
| BI и семантический слой, параметризованные запросы | Базовый выбор: определения метрик едины, ошибка воспроизводима | Ограничен каталогом готовых метрик | Не покрывает |
| Статистика, классическое ML | Не нужно | Не нужно | Подходит для прогноза (см. U09); данные и разметка в кейсе не заданы (gap) |
| Текст-в-SQL (один LLM-вызов) | Не нужен | Возможен как черновик запроса для аналитика | Не рекомендуется без проверки |
| RAG по документации схемы | Не нужен | Вспомогателен: описание таблиц и определений метрик | Вспомогателен |
| Фиксированный workflow: вопрос, выбор метрики из каталога, шаблон запроса, исполнение read-only, проверка | Возможен | Выбранный вариант | Нет |
| Агент с read-only инструментами | Избыточен | Допустим для разведочных вопросов с ограничениями и наблюдаемой обратной связью | Только как помощник аналитика |

Основание: [Anthropic](https://www.anthropic.com/research/building-effective-agents) (пакет R1, R1-C01, reported) советует начинать с простейшего решения и использовать агента, когда путь заранее не известен и есть наблюдаемая обратная связь; для повторяющихся вопросов путь известен. Контрдовод против вывода «агент всегда лучше»: R1-C13 (disputed) - тезис «ИИ всегда ускоряет» не поддерживается совокупностью прочитанного.

Выбранное решение: каталог метрик (BI или параметризованные запросы) для повторяющихся вопросов; для новых вопросов черновик SQL от модели, исполняемый только read-only инструментом с ограничениями и проверяемый аналитиком. Отвергнутая альтернатива: помощник с правом записи и произвольным доступом к базе, который сам исправляет данные и рассылает отчёты. Причины: изменение состояния и внешняя связь вместе с недоверенным вводом и чувствительными данными нарушают Rule of Two (R3-C3, reported, рекомендация вендора). Условие отказа от ИИ: если неверные числа с правдоподобным видом доходят до принятия без обнаружения, либо полное время вопроса (формулировка, проверка, переделка) выше baseline в двух периодах подряд, остаются отчёт и ручной SQL. Порог выбирает владелец метрики; общепринятого значения в источниках курса нет (gap).

## Данные и интеграции
- Происхождение: витрина или реплика только для чтения с описанием таблиц, владельцем и датой обновления; в упражнениях только синтетические SYN-TRIPS и SYN-REFUNDS, без реальных рейсов, билетов и клиентов.
- Контракт инструмента: вход (метрика из каталога или SQL, период), выход (строки, число строк, время исполнения, версия данных, текст запроса). Для tool-based доступа MCP описывает inputSchema и outputSchema, клиент должен валидировать выход ([MCP Tools](https://modelcontextprotocol.io/specification/2025-06-18/server/tools), SRC-17, R1-C05, verified); это контракт формы, а не правдивости и не авторизация (контрпример из curriculum M03: наличие MCP-сервера не система авторизации).
- Права: учётная запись запросившего определяет доступные таблицы и строки; роль базы с правом только SELECT на разрешённые представления; персональные поля исключены из представлений или маскированы.
- Точки человеческого решения: аналитик проверяет запрос и результат до публикации; любая публикация вовне и рассылка делаются человеком.
- Граница доверия: значения в ячейках, комментарии заказов и названия столбцов - данные, не команды.

## Безопасность
| Угроза | Контроль вне prompt | Негативный тест | Остаточный риск и владелец |
|---|---|---|---|
| Запрос на запись или удаление (DROP, UPDATE) от модели | Роль базы без прав записи; разрешены только SELECT по списку представлений; запрет множественных операторов | Запрос DELETE к SYN-TRIPS отклонён ролью, данные не изменены | Полнота настройки реальной базы unverified; владелец данных |
| Чтение закрытых данных («покажи все персональные поля») | Права по учётной записи, представления без персональных полей, ограничение числа строк | Запрос закрытого столбца возвращает отказ, а не данные | Утечка через агрегаты малых групп; владелец данных |
| Injection в данных (текст в ячейке просит выгрузить таблицу во внешний сервис) | Нет инструмента внешней отправки; исходящий трафик закрыт; trifecta (приватные данные, недоверенный контент, внешняя связь) не собирается ([Willison](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/), R3-C1, reported) | Строка с командой в SYN-REFUNDS не вызывает ни вызова, ни отправки | Полной защиты от injection никто не гарантирует (R3-C2, мнение); владелец безопасности |
| Дорогой или зависающий запрос | Лимит времени и строк на стороне базы, остановка по таймауту, понятный fallback «обратитесь к аналитику» | Запрос без фильтра по SYN-TRIPS прерван по лимиту | Параметры лимитов не заданы (gap); владелец платформы |
| Правдоподобное, но неверное число (не тот JOIN, не тот период) | Проверка результата: сверка итога с контрольной суммой по каталогу метрик, показ запроса и периода, ответ «не знаю» при несовпадении определения | Запрос с дублирующим JOIN, завышающий сумму, не проходит сверку | Согласованные ошибки определения не ловятся; владелец метрики |
| Эксплойт через доверенную платформу (аналог демонстрации [Invariant Labs](https://invariantlabs.ai/blog/mcp-github-vulnerability), R3-C5, C6, reported, независимо не воспроизведено) | Минимальные полномочия токена, подтверждение человеком нетипичных вызовов | Вызов вне белого списка инструментов блокируется | Привычка нажимать «всегда разрешать» (R3-C7, reported) не измерена; владелец безопасности |

Принуждение показывает только отказ реального исполнителя; здесь это simulation. KC-B08 (sandbox пути и сети, partial) и KC-A13 (payload недоверен, partial) указывают направление, но реальный отказ в этом кейсе не проверялся. SRC-12 - справочник по OWASP LLM Top 10 2025, не доказательство работы контролей.

## Инфраструктура
Минимум: реплика или представления только для чтения, роль базы с SELECT, каталог метрик с определениями и версиями, инструмент выполнения запроса с таймаутом и лимитом строк, журнал (кто, какой запрос, сколько строк, без значений), один вызов модели, способ выключить помощника. Размещение модели и данных кейс не определяет (gap): выбирает владелец данных, hosted API и self-hosted не равноценны по риску и цене. Облако, кластер, векторная база, многоагентная оркестрация и долговременная память не нужны: схема известна, вопросы короткие. Версионирование: каталог метрик, описание схемы и промпт имеют версии. Откат: выключение помощника возвращает отчёты и ручной SQL. Секреты доступа к базе не попадают в журнал и промпт.

## Проверка и экономика
Все числа иллюстративные (author example), не измерены. Условия сопоставимости: одна неделя, 40 вопросов, режим shadow.
- Baseline: 20 минут на вопрос аналитику, 10 процентов вопросов с исправлением после публикации.
- Каркас оценки: уровни из [Hamel Husain](https://hamel.dev/blog/posts/evals/) (SRC-24, R2-C01, reported, опыт одного кейса): L1 - проверки кодом (запрос только SELECT, итог совпал с эталоном, период указан), L2 - выборочная оценка трасс, L3 - сравнение на зрелом продукте. Раздельные наборы dev и holdout (curriculum M04); эталон можно начать с синтетики (R2-C04).
- Критерий принятия: ответ принят аналитиком без правок и итог совпал с эталонным запросом: 28 / 40 = 70 процентов (исправлено 9, отклонено 3).
- Полное время: формулировка 1 + проверка 6 + переделка 15 x 12 / 40 = 11,5 минуты против 20. Выигрыш держится на проверке.
- Контрпример: подготовка 3 минуты, проверка 10, исправление 12 минут у каждого второго вопроса дают 3 + 10 + 6 = 19 минут против 20, при риске необнаруженной ошибки; сопоставимо ли это с отчётом, не измерено.
- LLM-судья допустим только для критериев, которые нельзя проверить кодом, с калибровкой по разметке человека: сильный судья согласуется с людьми более чем в 80 процентах случаев, но есть position, verbosity и self-enhancement bias ([MT-Bench](https://arxiv.org/abs/2306.05685), SRC-28, R2-C03, reported, abstract, самоотчёт авторов).
- Стоимость токенов, задержка, точность текст-в-SQL на реальной схеме: не измерены (gap), относятся к M04 и M07.

## Связь с курсом и harness
- Модуль M03 (контракт данных, права при retrieval и повторном использовании памяти); M04 - evals; M05 - read-only исполнение и безопасность. Практикум: lab «Read-only помощник» ещё не создан (gap); в M03 используется только его идея в simulation.
- KC-Q01 (единый раннер evals, implemented по dry-run) и KC-Q04 (oracle, mutant, empty, implemented): проверка того, что набор вопросов ловит заведомо неверный запрос; подмену теста не ловит; качество моделей не измерено. KC-B08 и KC-A13 (partial) - направление принуждения, не доказанный отказ. KC-A37 (MCP-интеграции) имеет статус unverified, поэтому наличие MCP-доступа к базе не предполагается.
- Предложение (не миграция): добавить в карточку помощника поле «роль базы и список представлений» и обязательный негативный запрос на запись. Гипотезы KP к кейсу не привязаны (gap).
