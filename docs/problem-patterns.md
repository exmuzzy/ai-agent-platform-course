# Типовые задачи ИИ: подходы, безопасность и инфраструктура

Это обязательное техническое задание исследователям и авторам, а не утверждение о доказанном применении перечисленных методов во всех компаниях. Для каждой категории исполнитель должен найти актуальные реальные примеры и ограничения; названия технологий сами по себе не подтверждают промышленную зрелость.

## Как выбирать подход

Каждый кейс начинает с результата процесса и не-ИИ baseline. Сравнить только применимые варианты из ряда: правила/обычный код → статистика/классическое ML → LLM на одном шаге → RAG → фиксированный workflow → single-agent → multi-agent; это варианты, а не лестница обязательного усложнения.

Определить: тип и качество данных, проверяемость результата, цену ошибки, допустимую автономность, задержку, объём, интеграции, доступность людей для проверки и стоимость эксплуатации. RAG, fine-tuning и agentic orchestration решают разные задачи; автор обязан объяснить, когда ни один из них не нужен.

Для кейса нужен хотя бы один прочитанный первичный пример применения и независимое ограничение/альтернатива либо явно зафиксированный gap. Отделять production deployment, pilot, demo и vendor claim; не превращать «компания сообщила» в измеренный ROI.

## Практическое покрытие

Обязательные десять модульных лабораторных должны вместе воспроизводить четыре разных паттерна:

- **Знания и retrieval:** U01, разрешённые источники, устаревшие данные и отказ при отсутствии evidence.
- **Структурированные документы:** U02/U04, схема, валидация, трассировка требования и отказ при неоднозначности.
- **Разработка с проверками:** U03, изменение в sandbox, CI/test gate и запрет несогласованного merge/deploy.
- **Read-only операционный помощник:** U06/U07, ограниченный запрос, разграничение прав, trace, timeout и fallback.

Это четыре интегрированных примера внутри уже предусмотренных модулей, не четыре дополнительных курса. Использовать общий синтетический транспортный набор там, где это сохраняет различия задач; не выдавать один переименованный chatbot за четыре паттерна.

Обязательный offline-path проверяет код, контракты и контроль отказов. Качество генерации/распознавания/прогнозирования настоящей модели проверяется отдельно, с разрешёнными данными и compute; mock-ответы этого не доказывают.

## Безопасность в каждом кейсе

- **Данные:** классификация, минимизация, происхождение, права, retention и удаление.
- **Доступ:** identity, least privilege, tenant isolation, секреты, tool allowlist и исходящий трафик.
- **Недоверенный контент:** injection в документах и tool output, data poisoning, вредоносные зависимости и supply chain.
- **Действия:** точка человеческого approval, idempotency, dry-run, лимит ущерба и аварийная остановка.
- **Проверка:** минимум один негативный сценарий и enforceable контроль вне prompt.
- **Публичность:** отделение учебных fixtures от личной памяти, данных компании и чужого кода.

Для U09/U10 отдельно рассмотреть утечку обучающих данных, сдвиг данных и ошибку модели; не сводить всю безопасность к prompt injection. Не добавлять биометрию, финансовые списания или управление движением как автономный обязательный практикум.

## Инфраструктура как обязательный предмет

M02 и M06 должны содержать сравнение минимальной локальной, облачной и гибридной архитектуры. В каждом кейсе описать необходимые и ненужные компоненты с объяснением выбора; hosted API и self-hosted inference не являются автоматически равноценными по риску, цене и качеству.

| Слой | Что разобрать | Что проверить в учебном стенде |
|---|---|---|
| Модели и вычисления | Gateway, routing, версии, quotas, CPU/GPU/edge, latency/throughput и границы self-hosting | Pin/config; timeout, rate limit и безопасный fallback |
| Данные и контекст | Ingestion, object/SQL storage, retrieval/vector search при необходимости, кеш, retention | ACL, freshness, provenance и отсутствие межпользовательской утечки |
| Исполнение | Workers, очереди, state, checkpoint/replay, идемпотентность и ограничение fan-out | Crash после эффекта; reconcile вместо слепого повтора |
| Изоляция и доступ | Контейнеры/sandbox, сеть, egress, IAM, secrets, разделение сред | Запрет недопустимого tool call и выхода за sandbox |
| Поставка | Versioned code/model/prompt/data, CI/CD, тесты, canary и rollback | Совместимость, regression и возврат на baseline |
| Эксплуатация | Traces, metrics, logs, SLO, capacity, cache accounting и стоимость outcome | Связь task/model/tool; ошибки, нагрузочные пределы и runbook |

Docker, Kubernetes, конкретное облако, vector DB и inference server являются кандидатами для сравнения, не обязательной установкой всех компонентов. Учебный стенд должен оставаться небольшим; необходимость каждого дополнительного компонента обосновывается.

## Приёмка охвата

В `research/coverage.md` добавить ось U01–U12 и для каждой категории указать созданный case, подтверждённые источники, урок, безопасность, инфраструктурное решение и проверку понимания. Для четырёх обязательных паттернов дополнительно указать runnable lab и реальный статус evidence.

Нельзя принять курс, если он объясняет только создание агентов, не сравнивает подходы, сводит безопасность к текстовой инструкции или оставляет инфраструктуру набором названий инструментов. Неразрешённые gaps должны препятствовать заявлению о полной готовности соответствующей темы.
