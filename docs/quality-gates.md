# Критерии качества и приёмки

Проверки разделены на механические, содержательные и экспериментальные. Зелёный CI подтверждает только те свойства, которые он действительно проверяет; готовность курса принимает независимый reviewer по всем уровням.

## Gate G0: задания и входы

- **Scope:** указан task id, baseline и allowlist файлов; зависимости не цикличны.
- **Источники:** для авторства packet содержит проверенные URL/разделы; для discovery/research допустим вопрос и seed/gaps, не выдаваемые за проверенные claims.
- **Ресурсы:** authoring reservation и enforceable hard stop переданы в packet; live API-практикумы выключены либо разрешены с отдельным лимитом.
- **Роли/модели:** actual runtime profile проверен, authoring budget отделён от live-lab budget; fallback указан честно.
- **Harness:** для actual-harness задач checkout и права на экспорт проверены, изменения изолированы; безопасное авторство на synthetic path не требует недоступного checkout.

## Gate G1: отдельный урок

- **Learning outcome:** учащийся может назвать и выполнить проверяемое действие.
- **Аудитория:** указан USER/BUILDER/ENGINEER; неинженерный результат объясняется без обязательного разбора ядра, термины раскрыты.
- **Объяснение:** есть самостоятельная модель, пример и контрпример, а не только список ссылок.
- **Применимость:** показано, как использовать уже существующий harness без обязательной миграции на vendor framework.
- **Выбор подхода:** назван тип задачи U01–U12, сравнимый не-ИИ baseline и причины выбора/отказа от более автономного решения.
- **Достоверность:** внешние факты имеют первоисточник; рекомендации автора явно отделены.
- **Язык:** русский текст, терминология единообразна, аббревиатуры раскрыты.

## Gate G2: практикум

- **Запуск:** prerequisites, команды, input, expected output, reset/cleanup описаны.
- **Сотрудник:** шаги USER отделены от установки стенда инженером; доступ и интерфейс не выдуманы, личные ключи и кодинг не являются скрытым prerequisite.
- **Изоляция:** используются синтетические данные и безопасные эффекты.
- **Безопасность:** модель угроз, реальные границы доступа и негативная проверка релевантного контроля; обещание в prompt не является enforceable policy.
- **Инфраструктура:** названы минимальные компоненты и способ размещения; версии, доступы, telemetry и rollback не оставлены подразумеваемыми.
- **Failure case:** минимум один отрицательный сценарий и ясная ожидаемая реакция.
- **Evidence:** результаты реально получены на указанной версии; `not_run` не маскируется.
- **Повтор:** fresh-checkout исполнитель проходит задание без устных подсказок автора.
- **Если изменяется harness:** baseline, minimal diff, regression, независимое review и rollback; изменение ядра не является обязательным результатом USER/BUILDER.

## Gate G3: оценка знаний

Не менее шести вопросов, из них два ситуационных и один на поиск ошибки; ответы и рубрика находятся отдельно. Есть задача на перенос в иной контекст, не решаемая простым копированием примера.

Для каждого итогового артефакта задана шкала 0–3 и перечислены критические ошибки. Самопроверка допустима, но не подменяет независимую проверку курса как продукта.

## Gate G4: безопасность публикации

Проверены actual diff, права, синтетичность данных, отсутствие скрытых внешних подключений и секретов. Разрешение на публикацию harness учтено: собственный очищенный код не блокируется лишь потому, что раньше находился в приватном checkout.

Блокируют выпуск: credential/PII leak, чужой закрытый материал, обязательная небезопасная операция, выдуманный результат/ссылка, платный обязательный ресурс без альтернативы и предупреждения. Паттерн-сканер является вспомогательным, а не достаточным доказательством.

## Gate G5: целый курс

- **Покрытие:** M00–M09 имеют полный комплект, все учебные результаты связаны с проверками.
- **Маршруты:** готовы и независимо проверены `paths/USER.md`, `paths/BUILDER.md`, `paths/ENGINEER.md`; один длинный инженерный курс не заменяет их.
- **Первое применение:** правила безопасности предшествуют первой загрузке; проверены доступ, первый результат, остановка и поддержка либо явно указан gap.
- **Создание:** BUILDER сдаёт новую автоматизацию с тестами, владельцем и инструкцией по [карточке](../templates/automation-card.md), не только повторяет демо.
- **Возможности ядра:** каталог связан с модулями/кейсами и версией финального профиля; наличие в коде, доставка, проверки и права роли разделены.
- **Развитие:** предложения и roadmap содержат evidence, альтернативы, границу изменения, приоритеты, владельца, совместимость, тесты и откат; гипотеза не выдана за дефект или согласованное внедрение.
- **Индустрия:** source packets подтверждают чтение документации, статей, кода и обсуждений; coverage связывает все девять тем Сколково, интересы и результаты курса.
- **Типовые задачи:** созданы 12 case studies U01–U12 с источниками, альтернативами, безопасностью и инфраструктурой; четыре обязательных паттерна имеют runnable lab.
- **Связность:** общий кейс и имена артефактов не противоречат друг другу.
- **Открытый путь:** обязательный offline-маршрут воспроизводится из публичного checkout.
- **Версия:** окончательный harness/fixture включён до Q01; Q02/Q03 привязаны к release-candidate commit и не используются после существенного изменения содержимого.
- **Персонализация:** реальный harness обследован/экспортирован либо статус отсутствия явно указан; fixture не выдаётся за него.
- **Экономика:** стоимость принятых результатов учитывает ошибки и ручные проверки, сценарии не выданы за реальные показатели.
- **Capstone:** есть защита решения «не внедрять», а не только демонстрация успешного сценария.

## Статусы материалов

`planned`: есть brief; `draft`: написано; `reviewed`: прошла содержательная проверка; `mock_verified`: проверен offline-путь; `live_verified`: отдельно проверен model-backed путь с evidence. Эти статусы не смешиваются с task state и не присваиваются автоматически по числу файлов.

Версия 1.0 может быть обозначена «готова для offline-обучения» при `mock_verified` всех обязательных практикумов и честном описании live-ограничений. Если экспорт реального harness заблокирован, выпуск следует назвать fixture edition, а не выполнением обещания о публикации harness.

Готовность offline-материалов не равна готовности сотрудников использовать корпоративный сервис. В release evidence отдельно указываются `simulation_passed` и `approved_environment_passed`; второй статус требует реального проверенного пути доступа в разрешённой среде, без публикации внутренних адресов.

## Механические проверки стартового комплекта

```bash
python3 scripts/check_repo.py
python3 -m unittest discover -s tests -v
git diff --check
```

Текущий скрипт проверяет JSON, уникальность идентификаторов, ссылки на существующие модули/источники, DAG backlog, владельцев и write scopes U01–U12, локальные Markdown-пути и несколько чувствительных паттернов. Он не обращается к LLM, не выполняет упражнения и не гарантирует актуальность внешнего сайта или содержательную готовность кейсов.
