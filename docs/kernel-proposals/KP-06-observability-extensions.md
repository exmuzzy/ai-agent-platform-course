# KP-06: сопровождение и расширения

Статус: hypothesis. Автор: роль repo-analyst/architect. Дата: 2026-11-08. Baseline: публичный аудит (`docs/harness-baseline.md`). Capability: KC-A25, KC-A31, KC-A34, KC-A35, KC-A36, KC-A37.

## Потребность сотрудника

- ENGINEER разбирает, почему задача дала плохой результат: нужно связать задачу (task), прогон (run) и вызовы инструментов (tool) общим идентификатором.
- BUILDER хочет понять, сколько ресурсов ушло на принятый результат, а не на все попытки вместе.
- BUILDER подключает чужой skill, hook или MCP-сервер и хочет знать, что именно он получает и с какими правами.
- Сценарий: два прогона одной задачи, второй принят; usage первого и второго нужно разделить. Это гипотеза, дефект не доказан.

## Доказательство и неизвестное

| Слой | Что известно |
|---|---|
| Код | Парсер usage различает token usage и объём текста (KC-A25); hook имеет deny-envelope и fail-closed (KC-A31). |
| Схемы | Есть схема реестра хуков и описание пакетов (KC-A34, KC-A35). |
| Доставка | Установка расширений не запускалась. |
| Offline/live | Корреляция task/run/tool не проверялась. Реальные истории не читались. |
| MCP | Наличие MCP в ядре не установлено (KC-A37). |

Неизвестно, существует ли сквозной идентификатор и учитывается ли usage по принятому результату.

Индустрия:
- [MCP security best practices](https://modelcontextprotocol.io/specification/2025-06-18/basic/security_best_practices) описывают риски доверия к серверам и их инструментам.
- [Invariant Labs: MCP GitHub vulnerability](https://invariantlabs.ai/blog/mcp-github-vulnerability) разбирает атаку через недоверенный контент при широких правах инструмента.
- [OWASP Agentic Top 10 2026](https://genai.owasp.org/resource/owasp-top-10-for-agentic-applications-for-2026/) включает пункт про уязвимости цепочки поставок агентов (по R3 S10/C18 прочитано оглавление [PDF-зеркала](https://storage.ghost.io/c/44/95/449506ca-034e-480f-9725-fcde08ef1cc1/content/files/2026/02/OWASP-Top-10-For-Agentic-Applications-2026.pdf), где назван ASI04; описания рисков не прочитаны).
- Содержимое GenAI conventions OpenTelemetry не прочитано (доступна лишь страница Moved); сравнений с ними нет, требуется чтение.

## Варианты и граница изменения

| Вариант | Оценка |
|---|---|
| Не менять | Допустимо, если корреляция уже есть в журналах. |
| Обучение/документация | Описать, как вручную связать task/run/tool; чек-лист «что проверить перед подключением расширения». |
| Конфигурация | Включить существующие журналы, если они есть. |
| Шаблон/адаптер | Основной кандидат: шаблон run record (общий с KP-04) с полями task_id, run_id, tool_call_id, usage, accepted. |
| Сервис | Дашборды не добавляются без доказанной потребности. |
| Изменение ядра | Не предлагается. |

## Минимальное предложение

1. Контракт записи: task_id → run_id → tool_call_id, usage по каждому run, флаг принятия результата. Метрика «usage на принятый результат» считается из записей, а не хранится.
2. Контракт подключения расширения: манифест с источником, версией или хэшем, лицензией, запрашиваемыми правами и событиями. Подключение по умолчанию без записи на диск и в сеть, права повышаются явно, человек подтверждает.
3. Supply chain: расширение закрепляется по версии/хэшу, обновление проходит повторную проверку, непроверенный источник не подключается.
Не меняется: существующие hooks, пакеты, marketplace.

## Безопасность, инфраструктура и стоимость

Синтетические данные, секреты не логируются. Контроль: deny по умолчанию, журнал подключений. Остановка: отзыв расширения удаляет его из манифеста. Стоимость неизвестна; обещаний экономии нет. Измерения (usage) отделены от сценариев (что считать принятым).

## Приёмка, поставка и откат

- Positive: по записи восстанавливается цепочка task→run→tool.
- Negative: расширение без хэша или с лишними правами отклоняется; подмена содержимого после закрепления обнаруживается.
- Regression: подключение расширения не меняет поведение существующих hooks.
- Поставка: шаблон и чек-лист; откат: удаление шаблона.

## Приоритет и решение

Низкий-средний: приоритет по проверенным кейсам, метрики и плагины не добавляются без потребности. Вердикт сейчас: документация и шаблон записи; изменение ядра не предлагается. Владелец решения: ENGINEER, по вопросам безопасности расширений совместно с владельцем политики.

## Практикум и вопрос на понимание

Практикум (offline): сгенерировать синтетический журнал из двух прогонов одной задачи, вычислить usage на принятый результат; затем проверить три фиктивных манифеста расширений (с хэшем, без хэша, с чрезмерными правами) и объяснить решение по каждому. Предложение опровергнуто, если существующие журналы уже дают цепочку и принятый результат.

Вопрос для сотрудника без инженерной подготовки: «Коллега предлагает подключить готовое дополнение для ассистента. Какие три вещи вы спросите о нём до подключения?»
