# KP-02: обеспеченные полномочия

Статус: needs_validation. Автор: repo-analyst/architect (K00-P1). Дата: 2026-11-08. Baseline: `AUDIT-2026-11-08` ([harness-baseline](../harness-baseline.md)), текущая версия `unverified-current`. Capability: KC-A13, KC-A18, KC-A31, KC-A32, KC-A40, KC-B01, KC-B05, KC-B08, KC-A44.

## Потребность сотрудника

- **BUILDER.** Описывает в проекте, что агенту нельзя (пути, сеть, команды), и рассчитывает, что запрет действует. Сценарий: агент получает недоверенный текст с просьбой прочитать запрещённый путь; ограничение записано в политике, но неясно, остановит ли исполнитель действие.
- **ENGINEER.** Должен знать, на каком слое ограничение реально обеспечено.
- **USER.** Должен понимать, что просьба в промпте не равна запрету.

## Доказательство и неизвестное

Различаем пять слоёв: prompt (просьба модели), hook (код на событии клиента), policy-checker (функция, отвечающая allow/deny), runtime (режим разрешений исполнителя), ОС/контейнер (изоляция процесса). Только последние два обеспечивают запрет вне воли модели; hook обеспечивает его лишь для событий, которые клиент ему передаёт.

| Слой доказательства | Что известно | Что неизвестно |
|---|---|---|
| Код | В модуле sandbox политики путей и сети есть; по умолчанию режим advisory; для неизвестного runner есть permissive fallback. В просмотренном hook есть deny-envelope и fail-closed при внутреннем сбое | Обеспечивает ли это запрет на уровне ОС |
| Доставка | Hooks ставятся регистрацией в настройки клиента | Установлены ли они у сотрудника и покрывают ли все инструменты |
| Offline | Тестов на реальный отказ исполнителя в аудите нет | Исход запрещённого действия на синтетической среде |
| Live | Не проводилась | Поведение при cancellation и неизвестном runner |
| Сотруднику | Не проверена | Видит ли BUILDER, в каком режиме он работает |

Это наблюдение за поведением по умолчанию, не доказанный дефект: advisory может быть осознанным выбором, если ограничения обеспечиваются другим слоем.

Сравнение с индустрией: в [документации hooks](https://code.claude.com/docs/en/hooks) hook исполняет код на событии и блокирует через exit 2, то есть покрытие определяется событиями клиента; [lethal trifecta](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/) показывает, что защита строится снятием комбинации прав, а не просьбой модели; [рекомендации MCP по безопасности](https://modelcontextprotocol.io/specification/2025-06-18/basic/security_best_practices) описывают в прочитанной части угрозу confused deputy и необходимость согласия пользователя на уровне клиента; остальные тезисы этого пункта — авторские учебные принципы.

## Варианты и граница изменения

| Вариант | Оценка |
|---|---|
| Не менять | Допустим, если практикум покажет, что по умолчанию запрет действует |
| Обучение/документация | Обязательно: таблица «слой, что обеспечивает, чего нет» |
| Конфигурация | Включить enforcing-режим и отказ для неизвестного runner, если параметр уже есть |
| Шаблон/адаптер | Профиль исполнителя с deny по умолчанию |
| Сервис | Не нужен |
| Изменение ядра | Только если fallback нельзя закрыть конфигурацией |

Выбранный слой: конфигурация и документация; изменение ядра (fail-closed для неизвестного runner) только после подтверждённого воспроизведения.

## Минимальное предложение

Проверить контракт: неизвестный runner даёт deny либо явный отчёт «ограничение не обеспечено», а не молчаливый allow. Вход: политика и имя runner; выход: решение allow/deny и слой, который его обеспечил. Cancellation: остановка не должна оставлять частичное внешнее действие без reconcile. Не меняются существующие уровни автономии.

## Безопасность, инфраструктура и стоимость

Только синтетические пути и фиктивные секреты; никаких реальных учётных данных. Изоляция: контейнер без сети. Observability: журнал решения с указанием слоя. Остановка: прекращение эксперимента. Стоимость и трудоёмкость неизвестны.

## Приёмка, поставка и откат

- Positive: разрешённое действие проходит.
- Negative: запрещённое действие отклоняется исполнителем, а не только функцией проверки; неизвестный runner не получает молчаливого allow.
- Regression: внутренний сбой hook остаётся fail-closed; отмена не оставляет незавершённого действия.
- Откат: возврат прежнего режима политики; при неизвестном исходе внешнего действия обязателен reconcile.
- Поставка: сначала документация, затем конфигурация, затем (при необходимости) ядро, постепенно по клиентам.

## Приоритет и решение

Приоритет высокий и до live-практики (риск), уверенность evidence низкая. Следующий шаг: offline-практикум. Владелец решения: ENGINEER по безопасности; BUILDER получает правила для проектов. Вердикт: needs_validation; пока можно сделать только документацию различия слоёв.

## Практикум и проверка понимания

- **Практикум (ENGINEER, offline, синтетика).** В контейнере без сети запустить игрушечного исполнителя с политикой, запрещающей один синтетический путь. Проверить четыре случая: известный runner, неизвестный runner, внутренний сбой hook, отмена посреди действия. Фиксировать, какой слой остановил действие. Если неизвестный runner блокируется или явно помечается, предложение отклоняется; иначе обосновывается конфигурация либо правка ядра.
