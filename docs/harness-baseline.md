# Стартовое обследование harness для курса

Дата среза: 8 ноября 2026 года. Это очищенное резюме целевого чтения настоящих `harness` и `harness-kernel` на выбранном владельцем Mac и нескольких изолированных проверок, а не аудит всей системы или сертификат готовности к эксплуатации.

**Главный вывод: курс следует строить на существующих механизмах, а не создавать ещё один harness.** Уже есть код маршрутизации, восстановления workflow, оценки результатов, доставки ядра и инфраструктурных компонентов; при этом переносимость, фактическое обеспечение ограничений и пригодность для общего динамического процесса требуют отдельных доказательств.

## Статус и происхождение

- **Источник:** настоящие локальные checkout, не сторонний репозиторий и не демонстрационная замена. Полные пути, версии и технические свидетельства сохранены в отдельном отчёте владельца; публичный идентификатор среза: `AUDIT-2026-11-08`.
- **Способ работы:** чтение инструкций, выбранных участков кода, тестов и шаблонов; изолированные проверки на подставном хранилище и синтетических данных. Истории сессий, клиентские документы и файлы с секретами не запрашивались.
- **Изменения:** исходный код и конфигурация на Mac не изменялись. Commit и количество записей изменений в обоих checkout в начале и конце обследования совпали.
- **Граница доказательства:** тесты запускались в checkout ядра; выборочно сопоставленные с рабочим harness файлы оркестратора, reducer, dispatch, routing, eval и sandbox совпали побайтово. Это не проверка всего установленного дерева и не запуск рабочего workflow.
- **Публикация:** сюда не экспортированы исходники, исходная Git-история, внутренние адреса, идентификаторы проектов или реальные данные. Публичный runnable-профиль ещё не создан.

Этот файл является предварительным входом F01/F04. F00, F01 и остальные задачи авторства не помечаются выполненными: следующий исполнитель должен проверить свежесть среза, доступность источников и применимость выводов к своей среде.

После уточнения целевой аудитории курсы предназначены сотрудникам USER/BUILDER/ENGINEER. Текущее обследование ядра не проверяло регистрацию сотрудника, каталог готовых сценариев, конструктор и самостоятельное прохождение пользовательского пути; эти возможности остаются `unverified` по [onboarding contract](employee-onboarding.md).

## Что обязательно учесть при создании курса

- **Согласованность инструкций:** старые и новые документы расходятся в том, где является источником истины код ядра. До учебного patch исполнитель фиксирует владельца изменения и действующий путь доставки; не меняет оба дерева одновременно.
- **Воспроизводимость:** lock одного runtime не доказывает закреплённость всех эффективных инструкций. В M00/M02 нужны manifest источников, разрешение symlink/import цепочек и проверка независимого клиента.
- **Реальные ограничения:** prompt, hook, policy-checker, permission mode CLI и OS/container isolation являются разными слоями. В M05 нужно показать отказ реального исполнителя на запрещённом действии, а не только ответ функции проверки.
- **Оркестрация:** готовый `/ship` нельзя механически запускать для написания курса, поскольку его этапы включают внешние операции разработки. Применять протокол курса поверх разрешённых примитивов; поддержку DAG, остановки и сохранения бюджета проверять отдельно.
- **Качество оценки:** oracle/mutant/empty полезны, но недостаточны против изменения проверок самим исполнителем. Нужен дополнительный отрицательный кейс с подменой теста и независимая проверка целостности доверенного грейдера.
- **Инфраструктурный профиль:** в коде авторизации есть разные ветки для выключенной, частичной и полной конфигурации. Учебный профиль должен явно определить безопасное поведение и тестировать эти состояния, не наследовать молча настройки личного окружения.
- **Бюджет:** выбор модели по квоте, timeout этапа и общий authoring budget не взаимозаменяемы. Подтвердить измеримый hard stop и сохранение reservations/consumed/repair counters после resume.
- **Граница курса:** личный coding harness является инженерной лабораторией, а не доказанной платформой для всех процессов предприятия. Стратегия, владельцы процессов, данные, организационные изменения и 12 классов задач остаются обязательными.

## Следующие действия

1. В F01 проверить свежесть среза и дополнить неизвестные возможности, не повторяя весь поиск без необходимости.
2. В F03 использовать [карту практикумов](harness-course-map.md) при сборке общего fixture contract.
3. В F04 выбрать минимальный экспортируемый набор, проверить права, зависимости и инструкции, затем создать самостоятельный учебный профиль.
4. В M00/M04 воспроизвести offline-проверки уже из публичного профиля. До этого результаты выше нельзя выдавать за воспроизводимые из данного GitHub-репозитория.
5. В Q02/Q03 проверить точный release-candidate после включения экспорта; следовать существующей [политике работы с harness](harness-adapter.md).

Этот аудит не запускает генерацию курса, не закрывает задачи backlog и не разрешает незаявленные расходы. Новые исследования индустрии и программы Сколково остаются отдельной работой F02.
