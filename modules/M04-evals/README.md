# M04. Evals и выбор конфигураций

Статус: draft. Модуль учит связывать оценку с результатом задачи (outcome), а не с красотой ответа, и выбирать менее дорогую конфигурацию только если она не опускается ниже заранее заданного порога качества. Оценщик (тест, правило или LLM-judge) тоже может ошибаться, поэтому его проверяют отдельно. Всё практическое выполняется как симуляция (mode: simulation) на синтетических данных; живые вызовы моделей и API не используются.

Кейсы модуля: U03 (разработка и тестирование ПО) и U11 (подготовка контента и коммуникаций). Оба примера в уроках являются авторскими (author example), числа в них вымышлены.

Оценка времени (предварительная, измерить на пилоте): USER 100–120 минут = L01 35 + L02 35 + практикум 30–50; это уроки и практикум без итоговой проверки. Итоговая проверка (тест около 15 минут и обязательное открытое задание около 20 минут для USER, предварительные оценки) добавляет примерно 35 минут: полный USER total 135–155 минут. Для BUILDER и ENGINEER итоговая проверка также не входит в диапазоны ниже и добавляется отдельно. BUILDER 140–170 минут = 100–120 общих + 40–50 на набор кейсов и приёмку. ENGINEER 170–200 минут = 100–120 общих + 70–80 на инженерные блоки.

## Результат по ролям

- USER: отличает успех задачи от успеха инструмента, читает отчёт о сравнении (число кейсов, число запусков, неопределённость), знает, почему «модель-судья согласна на 95%» ещё ничего не доказывает, и не принимает вывод «дешевле значит лучше» без порога качества.
- BUILDER: дополнительно собирает набор кейсов (положительные, отрицательные, неоднозначные), разделяет development и holdout, пишет явную рубрику и условие приёмки для своей автоматизации.
- ENGINEER: дополнительно проверяет сам оценщик на вариантах oracle, mutant, empty и подмены теста (KC-Q04, KC-Q03, предложение KP-04), читает run record (KC-Q05) и не заявляет статистическую достаточность без обоснования.

Для USER инженерные блоки необязательны.

## Что модуль не обещает

- Не доказывает качество реальных моделей: данные синтетические, результаты симуляции заранее записаны (mock), live-проверки не было.
- Учебные размеры наборов (10–15 кейсов development, 20–30 для baseline, не менее 10 в holdout) являются минимумом для обучения, а не доказательством статистической достаточности для production.
- Не называет победившую модель или поставщика: выбор зависит от задачи, порога качества и цен на дату решения.
- Состояние ядра описано не выше статусов в каталоге возможностей: единый раннер, режимы oracle/mutant/empty реализованы (implemented), а состав held-out и защита от подмены теста не подтверждены (unverified).

## Критерии завершения

- Пройдены уроки M04.L01 и M04.L02 и практикум M04.LAB1.
- Выполнены активности M04.A01–M04.A06 (список в конце урока M04.L02), включая отрицательный сценарий.
- Пройден тест (вопросы M04.Q01–M04.Q10) с порогом по quiz.json; критические вопросы без ошибок.
- Вывод, который нельзя делать: «конфигурация B доказанно не хуже A в production». Симуляция на маленьком наборе этого не показывает.
