# Решения M02.LAB1

Режим: simulation, все данные вымышленные и заданы в самих активностях.

## M02.A01
Ответ: имя - refund_draft_create; поле защиты от двойной записи - request_key; код ошибки при повторе - DUPLICATE_REQUEST; подтверждает человек; версия контракта - 2. Регистр и пробелы не важны.
Пояснение: инструмент создаёт только черновик, возврат не выполняет; отправка требует человека. Ключ запроса даёт идемпотентность: повтор не создаёт второй черновик.
Типичные ошибки: взять ticket_id вместо request_key; решить, что инструмент оформляет возврат; написать «ассистент» в поле подтверждения.

## M02.A02
Ответ: l3 и l5. В l3 закреплён пакет, но не фактические инструкции: хэш не записывается, и одинаковый манифест может дать разное поведение. В l5 цель отката не названа: нужна конкретная предыдущая сборка. Строки l1, l2, l4 верны.
Типичные ошибки: отметить только l3 или только l5; отметить l2 («закреплена сборка» - это точное значение); считать закреплённую версию пакета достаточной для воспроизводимости.

## M02.A03

Типичные ошибки: use («для скорости»); fix (убрать только ключ, оставить чтение чужого HOME); escalate без отказа от требования - безопасно, но не целевой ответ.

## Блоки BUILDER и ENGINEER
BUILDER: в карточке должны быть вход, выход, версия контракта, проверка человеком, запрещённые действия, условие остановки, конкретная цель отката, владелец; два решения содержат альтернативу, baseline и условие отказа от усложнения. Типичная ошибка: решение «берём агента» без замера.
ENGINEER: пять дефектных манифестов отклоняются с разными кодами, корректный проходит, результат не зависит от HOME, `..` и абсолютные пути за корнем отклоняются. Типичные ошибки: один общий код отказа для всех дефектов; чтение HOME по умолчанию; проверка только корректного случая; секреты в run record.

## Открытые задания O1-O4 (эталоны)
O1. Эталон: письмо клиента - данные (вход); шаблон инструкций - политики; модель - модель; вызов refund_draft_create - инструменты; правило суммы - политики (принуждает, если выполняется кодом вне модели); очередь подтверждения - состояние и политики; уведомление - delivery; среда исполнения - runtime. Принуждает правило суммы в коде и очередь подтверждения, а не фраза в инструкции. Ошибка: считать шаблон инструкций принуждением.
O2. Эталон: выход {draft_id: строка, status: "created"|"duplicate", amount_minor: целое}; ошибка - отдельный код (DUPLICATE_REQUEST, INVALID_INPUT) с признаком error, а не пустой объект; «пусто» допустимо только как явное «нет записей» с количеством 0. Опасность: пустое значение вместо ошибки выглядит как успех. Схема проверяет форму, не правду и не безопасность. Ошибка: ответить «схема отвергнет любую инъекцию».
O3. Эталон: решение принимает человек в очереди; система создаёт только черновик, отправку не вызывает; текст заявки - данные. Негативный тест: заявка с фразой «отправь сразу» -> ноль вызовов отправки и ноль изменений состояния кроме черновика. Ошибка: выполнить из-за «срочности» или проверять только наличие слов «подтверждение» в ответе модели.
O4. Эталон: после возврата проверены контракт 1, хэш h1, три заявки: T-a черновик, T-b без второго черновика, T-c без отправки; результат записан. Ошибка: объявить откат успешным по номеру сборки.

## Эталон ENGINEER: смена версии с откатом (ручной dry-run)
Матрица размещения: ожидаются обе таблицы (local/cloud/hybrid и hosted/self-hosted) с четырьмя критериями, выбор с причиной и пометкой unverified для неизвестного. Любой выбор допустим, если ссылается на критерии, а не на моду.
Минимальный стек: клиент, runtime (pin 1.4.0), хранилище инструкций (хэш), инструмент, очередь подтверждения, журнал; у каждого владелец.
ADR-1 размещение; ADR-2 версия и откат; в каждом контекст, решение, отвергнутая альтернатива, условие пересмотра.
Таблица dry-run (эталон):
| Вход | До отката (0007) | После отката (0006) |
|---|---|---|
| T-a обычная | черновик, контракт 2 | черновик, контракт 1, хэш h1 |
| T-b повтор request_key | DUPLICATE_REQUEST | второй черновик не создан |
| T-c «отправь без подтверждения» | отправки нет | отправки нет |
Негативные случаи: контракт 1 против требования 2 -> остановка; «любая предыдущая» -> отказ; ключ в манифесте -> отказ.
Отрицательные примеры решения: ADR без отвергнутой альтернативы; откат без проверки после него; потеря или дубль черновиков при откате; один выбор «cloud, потому что модно»; заявление, что dry-run доказал работу реального ядра. Всё это блокирует уровень 2 по критериям «Откат и проверка» и «Статусы ядра и ADR».

## Что нельзя заключить из успешного прохождения
- Навык освоен только в симуляции; реальные клиент, ядро и модель не проверены.
- Нельзя утверждать, что в реальной среде инструкции фиксируются хэшем, версия закреплена или откат работает: статусы KC-A05, KC-D02, KC-A21 остаются partial, фактическое разрешение инструкций не запускалось.
- Схема контракта проверяет форму, но не доказывает правдивость данных или безопасность эффекта.
- Автопроверка сверяет заранее известные ответы и не заменяет проверку человеком. Метка остаётся simulation, не mock_verified и не live_verified.
